# 氛围层方案（atmosphere）

> 基于 2026-11-21 对当前 43 幕的实测。每条写明：现状 → 设计决策 → 为什么 → 验收 → 风险。

---

## 一、要解决的问题

现在 14 位化身、43 幕，全部是「旁白 + 抉择 + 后果」。但托尔金最迷人的部分不在决策，而在**环境本身**：摩瑞亚的黑暗有重量，洛汗的草原有风的味道，尸罗的巢穴有气味。

现状证据：每幕只有 `narration`（49–85 字）承担全部氛围，而它同时要交代**情境 + 前因 + 抉择压力**，三者挤在一段里，留给感官描写的空间几乎没有。

**目标**：给每幕加一层可选的「场景细读」，让玩家在抉择前能先「站进去」。

---

## 二、设计决策

### 2.1 数据结构

```js
{
  id: 'fr4', title: '末日火山', tier: 3,
  narration: '...',            // 现有：情境与压力
  atmosphere: {                // 新增：感官层
    sight: '火光从裂缝里渗出来，把岩石照成暗红色',
    sound: '地底有低沉的轰鸣，像某种呼吸',
    touch: '空气烫得喉咙发干，脚下的石头是温的',
    smell: '硫磺味',           // 可选
  },
  atmosphereNote: '末日火山的描写主要来自电影与读者的想象，原著着墨克制。', // 可选：来源标注
}
```

**为什么分感官字段而不是一段散文**：
- 分开写能强制作者真的去想「声音是什么」，而不是堆形容词
- UI 可按需选择展示几项
- 空字段可省略，不强制每个地点都有气味

### 2.2 渲染位置与形态

放在 `narration` **之后**、`stakes` **之前**，用原生 `<details>` 折叠，默认**收起**。

**为什么不默认展开**：40+ 幕如果每幕都先展开一大段描写，会稀释抉择的紧迫感。折叠让玩家自己选择「先感受」还是「直接选」。

**为什么用 `<details>`**：原生元素自带展开/收起、键盘可达、屏幕阅读器语义正确。不需要写状态，不需要 aria 特殊处理。

### 2.3 与既有机制的边界

| 问题 | 决策 |
|---|---|
| 是否影响评分？ | **不影响**。氛围是阅读层，不参与 `judgeJourney` |
| 是否受剧透等级控制？ | **不单独控制**。幕本身受 tier 过滤，幕内的氛围随之出现 |
| 是否必填？ | **可选**。缺失时该幕不渲染折叠块 |
| 是否进 API？ | 是，`avatarJourney` 返回，但 `avatarList` 不返回（列表不需要） |

### 2.4 来源诚实性

有些氛围来自电影（如末日火山的视觉），有些是原著的直接描写（如摩瑞亚），有些是我基于地点的合理推想。

**决策**：不逐条标注来源（那会让 UI 变成脚注墙），但在 DETAIL 文档里统一说明——氛围层是"基于原著与改编的合理想象"，不是原文摘录。个别差异大的会用 `atmosphereNote` 注明。

## 三、工作量与覆盖策略

43 幕全部写 = 43 × 4 感官 ≈ 172 条短句。这是本次最大工作量。

**策略：分层交付**

| 层 | 范围 | 理由 |
|---|---|---|
| 必做 | 所有 `tier: 3` 的高潮幕（共 14 幕） | 情绪最重、最需要氛围支撑 |
| 次做 | 所有 `tier: 1` 的开场幕（共 9 幕） | 建立第一印象 |
| 补齐 | 其余 `tier: 2`（共 20 幕） | 完成全覆盖 |

先做前两层（23 幕），验证 UI 与校验，再补齐剩余 20 幕。这样 UI 问题能早发现，不会等写完 172 条才发现字段拼错。

---

## 四、验收标准

- [ ] 43 幕中至少 23 幕有 atmosphere，最终目标 43 幕全覆盖
- [ ] 有 atmosphere 的幕，至少包含 `sight` 与 `sound` 两个字段
- [ ] 每条感官描写 15–60 字（太短无信息量，太长喧宾夺主）
- [ ] 折叠块默认收起，点击可展开，键盘可操作
- [ ] 不影响评分：`judgeJourney` 结果与加氛围前逐字节一致（用固定输入回归）
- [ ] `avatarList` 不包含 atmosphere（避免列表载荷膨胀）
- [ ] 缺失 atmosphere 的幕正常渲染，无空白块

---

## 五、风险

| 风险 | 对策 |
|---|---|
| 文案质量参差，变成凑字数 | 每条必须含至少一个**具体**感官细节（温度/材质/气味），禁止"美丽的""壮观的"这类空词 |
| 与原著冲突 | 拿不准的加 `atmosphereNote` 说明是推想 |
| 单文件膨胀 | `journey.js` 会从 590 行增到约 1100 行。尚可接受；到 1500 行时考虑拆分 |
| 内联块再次变大 | `client.js` 现 88KB，加氛围 UI 约 +3KB。仍在可接受范围 |

## 六、审核（写码前自查，发现 4 个问题）

### 漏洞 1：`<details>` 在没有 CSS 时会渲染成丑陋的原生块

**问题**：方案说"用原生 `<details>`，自带样式"。实际原生 details 的三角标记、边框、默认字体与大观感完全不匹配，会在暗色主题下非常突兀。

**修正**：必须写配套 CSS（`summary` 去默认标记、加自定义箭头、token 化配色），约 15 行。原方案漏了这部分工作量。

### 漏洞 2：45 字限制与我自己的写作习惯冲突（中）

**问题**：方案写"15–60 字"，但实测现有 `narration` 平均 65 字。如果氛围每条 60 字 × 4 感官 = 240 字，比旁白还长，会喧宾夺主。

**修正**：收紧到 **每感官 12–32 字**，四项合计不超过 100 字。氛围是"提示"不是"重写旁白"。

### 漏洞 3：遗漏了 `avatarJourney` 的 tier 过滤路径（中）

**问题**：`avatarJourney` 里场景是 `.map()` 构造的，新增字段必须显式加进返回对象，否则前端拿不到。方案只说"进 API"，没指明**在哪一层加**。

**明确的三个改动点**：
1. `journey.js` 数据层：场景对象加 `atmosphere`
2. `engine.js` `avatarJourney()` 的 `.map()`：`atmosphere: scene.atmosphere || null`
3. `avatar-tab.js` 渲染：条件渲染折叠块

### 漏洞 4：回归测试方式不可靠（高）

**问题**：方案验收写"`judgeJourney` 结果与加氛围前逐字节一致"。但 `judgeJourney` 返回对象含 `decisions` 数组，序列化时字段顺序可能变化，"逐字节"过于严格；而且没有记录基线。

**修正**：改为**行为断言**而非字节比对：用固定的全原著选择，断言 `ratio === 1 && diverged.length === 0`；用全黑暗选择，断言 `ratio === 0`。这两条已在 selfcheck 中，加氛围后必须仍然成立——**这就是回归保护**，不需要新基线。

### 补充：字段命名与既有数据的一致性

现有场景字段是扁平 camelCase（`narration`、`stakes`）。`atmosphere` 用嵌套对象是一致的，但**感官键名要用形容词化的名词**（`sight`/`sound`/`touch`/`smell`），不要用 `visual`/`audio`——前者是读者语言，后者是工程语言。
